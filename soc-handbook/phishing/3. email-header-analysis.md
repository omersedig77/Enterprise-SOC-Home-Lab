# Email Header Analysis

## Overview

Email header analysis is the process of examining the technical metadata attached to an email to determine:

- Where the email originated
- Which mail servers handled the message
- Whether the sender is legitimate
- Whether authentication checks passed
- Whether the email was spoofed
- What infrastructure the attacker used

Unlike the visible email content, headers provide technical evidence about the actual path and origin of the message.

SOC analysts use email headers during phishing investigations to validate sender identity, extract indicators of compromise (IOCs), and determine whether an email is malicious.

# Important Email Header Fields

---

# From

## Purpose

Shows the sender displayed to the user.

Example:

```
From:
Microsoft Security <security@microsoft.com>
```

---

## Investigation

Do not trust this field alone.

Attackers can spoof:

```
From: security@microsoft.com
```

while actually sending from:

```
attacker@gmail.com
```

The From field must be compared with:

- Return-Path
- SPF
- DKIM
- DMARC
- Received headers

---

# Return-Path

## Purpose

Shows where delivery failures are sent.

Example:

```
Return-Path:
attacker@malicious-domain.com
```

---

## SOC Importance

A mismatch between:

```
From:
security@microsoft.com

Return-Path:
attacker@malicious-domain.com
```

is suspicious.

This is commonly seen in spoofing attempts.

---

# Reply-To

## Purpose

Defines where replies are sent.

Attackers commonly abuse this field.

Example:

```
From:

billing@paypal.com


Reply-To:

payment-team@gmail.com
```

The victim believes they are contacting PayPal, but replies go to the attacker.

---

# Received Headers

## Purpose

The Received headers show the path an email traveled through.

Example:

```
Received:
from mail.example.com
by mx.google.com
```

Every mail server adds a Received entry.

---

# Reading Received Headers

Important information:

- Sending server
- Receiving server
- IP address
- Timestamp
- Mail path

The earliest Received entry is usually closest to the original sender.

Example:

```
Received:
from attacker-mail.com
(185.xxx.xxx.xxx)

by victim-mail-server.com
```

The IP:

```
185.xxx.xxx.xxx
```

may represent the attacker infrastructure.

---

# Investigating Sending IP Address

After extracting the sending IP, investigate:

Questions:

- Is the IP associated with spam?
- Is it a known malicious server?
- Is it a VPN/proxy?
- Is it a cloud provider?

Useful sources:

- VirusTotal
- AbuseIPDB
- AlienVault OTX
- Cisco Talos

---

# SPF (Sender Policy Framework)

## Purpose

SPF verifies whether the sending mail server is authorized to send email for a domain.

Example:

Domain:

```
example.com
```

SPF record:

```
Only mail server X can send email.
```

---

# SPF Results

## Pass

The sending server is authorized.

Example:

```
spf=pass
```

---

## Fail

The sending server is not authorized.

Example:

```
spf=fail
```

Strong phishing indicator.

---

## SoftFail

The sender is suspicious but not completely rejected.

Example:

```
spf=softfail
```

---

## None

No SPF record exists.

Example:

```
spf=none
```

---

# SPF Limitations

SPF does not prove:

- The sender is trustworthy
- The email content is safe
- The account was not compromised

A compromised legitimate mail server can still pass SPF.

---

# DKIM (DomainKeys Identified Mail)

## Purpose

DKIM adds a cryptographic signature to emails.

The receiving server verifies:

- Message integrity
- Domain ownership

---

Example:

```
DKIM-Signature:
d=example.com
```

---

# DKIM Results

## Pass

The email signature is valid.

```
dkim=pass
```

---

## Fail

The signature is invalid.

```
dkim=fail
```

Possible causes:

- Email modification
- Spoofing
- Invalid signature

---

# DMARC (Domain-based Message Authentication Reporting and Conformance)

## Purpose

DMARC combines:

- SPF
- DKIM

and defines what happens when authentication fails.

---

# DMARC Policies

## None

Monitoring only.

```
p=none
```

---

## Quarantine

Suspicious messages should go to spam.

```
p=quarantine
```

---

## Reject

Reject failed emails.

```
p=reject
```

---

# Authentication-Results Header

This is one of the most important fields.

Example:

```
Authentication-Results:

spf=fail

dkim=fail

dmarc=fail
```

This strongly indicates spoofing.

---

# Message-ID

## Purpose

Unique identifier generated by the sending mail system.

Example:

```
Message-ID:
<12345@mail.example.com>
```

---

# Investigation

Check:

- Does the domain match the sender?
- Is the Message-ID from a suspicious domain?
- Are multiple phishing emails using similar IDs?

Example:

Legitimate:

```
Message-ID:
abc123@microsoft.com
```

Suspicious:

```
Message-ID:
abc123@gmail.com
```

when claiming to be Microsoft.

---

# MIME-Version

Shows email formatting standard.

Example:

```
MIME-Version:
1.0
```

Usually not malicious alone, but useful when analyzing attachments.

---

# Content-Type

Shows message format.

Examples:

```
text/plain

text/html

multipart/mixed
```

---

Suspicious indicators:

```
multipart/mixed
```

with:

- Executable attachments
- Macro documents
- Archives

# Example Suspicious Header Analysis

## Header

```
From:
Microsoft Security <security@microsoft-alerts.com>


Return-Path:
support@gmail.com


Received:
from unknown-server
(45.23.55.10)


Authentication-Results:

spf=fail

dkim=fail

dmarc=fail
```

---

# Analyst Findings

## Sender

Suspicious.

Reason:

Domain:

```
microsoft-alerts.com
```

is not Microsoft official infrastructure.

---

## Return-Path

Mismatch detected.

From:

```
microsoft-alerts.com
```

Return:

```
gmail.com
```

---

## Sending IP

Investigate:

```
45.23.55.10
```

Check reputation.

---

## Authentication

Results:

```
SPF Fail

DKIM Fail

DMARC Fail
```

Strong indication of spoofing.

# Common Phishing Header Indicators

| Indicator | Meaning |
|---|---|
| SPF Fail | Unauthorized sender server |
| DKIM Fail | Invalid signature |
| DMARC Fail | Domain authentication failure |
| From/Reply-To mismatch | Possible phishing |
| Unknown sending IP | Suspicious infrastructure |
| Recently created domain | Possible attacker domain |
| Multiple Received hops | Possible obfuscation |
| Free email provider | Possible impersonation |

# Threat Intelligence Investigation

After identifying:

- Sending IP
- Domain
- URLs
- Hashes

Search:

## IP Reputation

Questions:

- Is this IP malicious?
- Previous phishing activity?
- Hosting provider?

---

## Domain Reputation

Questions:

- When was the domain created?
- Who owns it?
- Previous abuse reports?

---

## Hash Reputation

Questions:

- Is attachment malware?
- Malware family?
- Previous detections?

# Key Takeaways

Email headers provide valuable forensic evidence during phishing investigations.

A SOC analyst should never rely only on the visible email content. Proper analysis requires:

- Header inspection
- Authentication validation
- Sender verification
- Infrastructure analysis
- Threat intelligence enrichment
- IOC extraction

Header analysis allows defenders to identify phishing campaigns, track attacker infrastructure, and prevent additional compromise.
